# Общие принципы и процесс изменения кода

## Приоритеты

1. Корректность и сохранение ожидаемого поведения.
2. Безопасность данных и границ доступа.
3. Читаемость, простота и предсказуемость.
4. Поддерживаемость и согласованность с проектом.
5. Производительность, если есть основание для оптимизации.

## Анализ перед разработкой

- Сначала изучи ближайшие зависимости, аналоги, тесты и соглашения.
- Не переименовывай файлы и публичные символы без причины.
- Изменяй только связанный с задачей код.
- Не переписывай модуль ради одного исправления.
- Не устанавливай пакет, если уже есть подходящий инструмент.
- Изменение поведения, данных и контрактов отмечай явно.

### Пример: кнопка удаления задачи

**Плохо:** создать новый Button, собственный HTTP-клиент и новый store, не изучив проект.

**Хорошо:** использовать существующие Button, API-клиент и механизм обновления данных; исправить только нужные модули. Но компонент Button не должен становиться "Бог-компонент" и отвечать за все состояния сразу.

## KISS — простота

Плохо:

```ts
const isActive = Boolean(Boolean(user?.status === 'active') === true);
```

Хорошо:

```ts
const isActive = user?.status === 'active';
```

Сложность допустима там, где она решает конкретную проблему, а не ради архитектурной моды.

## DRY — не дублируй знание

Плохо:

```ts
const userName = `${user.firstName} ${user.lastName}`;
const adminName = `${admin.firstName} ${admin.lastName}`;
```

Когда правило форматирования действительно одно:

```ts
type Person = { firstName: string; lastName: string };

function getFullName(person: Person): string {
  return `${person.firstName} ${person.lastName}`;
}
```

Но не объединяй похожие фрагменты, если они имеют разные причины изменения.

## YAGNI — не проектируй невостребованное

Если нужна сортировка задач по дате, не создавай универсальный механизм сортировки всех будущих сущностей.

## SOLID в прикладном коде

- **S:** разделяй разные причины изменения; HTTP, бизнес-правила и работа с БД — разные обязанности.
- **O:** предусматривай расширение лишь когда оно реально ожидается.
- **L:** сохраняй заявленные контракты и корректную подстановку реализаций.
- **I:** небольшие интерфейсы уместны, если потребителям нужны разные возможности.
- **D:** зависимость от контракта полезна на границах заменяемых компонентов; не вводи её механически.

Пример: контроллер не должен одновременно валидировать вход, вычислять бизнес-правила, работать с Prisma и отправлять email. Однако не обязательно создавать класс и интерфейс для каждой функции.

## Именование и комментарии

Плохо:

```ts
const x = users.filter(u => u.a);
```

Лучше:

```ts
const activeUsers = users.filter(user => user.isActive);
```

Комментарии объясняют *почему*, а не пересказывают очевидную строку. Имена переменных, функций, типов и файлов — на английском, если в проекте нет других соглашений.

## Работа с ошибками

- Не оставляй пустой `catch`.
- Не подавляй диагностику линтера/TypeScript без веского объяснения.
- Не подменяй проверку реального поведения предположением.
- Не заявляй об исправлении без подтверждения в доступных проверках.
