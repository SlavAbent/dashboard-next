# Code Review: React и Next.js

## Чек-лист React
1. React — компоненты и хуки
- Не вызываются ли хуки внутри условий, циклов, обработчиков событий или вложенных функций?
- Сохраняется ли одинаковый порядок вызова хуков при каждом рендере?
- Не вызываются ли хуки после условного return?
- Не используются ли React-хуки вне React-компонентов или пользовательских хуков?
- Корректно ли используются use(), useEffect(), useLayoutEffect() и другие API с учётом версии React?
- Не содержит ли useEffect логику, которую можно выполнить непосредственно при рендере или в обработчике?
- Все ли реактивные зависимости указаны в массиве зависимостей?
- Возможен ли stale closure в эффектах, таймерах, подписках или обработчиках?
- Не создаёт ли эффект бесконечный цикл обновлений?
- Не запускаются ли повторные запросы без необходимости?
- Очищаются ли setTimeout, setInterval, WebSocket, подписки и event listeners?
- Используется ли AbortController или другой механизм предотвращения устаревших запросов там, где это необходимо?
- Нет ли race condition при нескольких асинхронных операциях?
- Корректно ли работает эффект при повторном setup/cleanup в StrictMode?
- Не выполняются ли побочные эффекты непосредственно во время рендера?
- Не мутируется ли состояние напрямую?
- Не используется ли устаревшее значение состояния при нескольких последовательных обновлениях?
- Применяется ли функциональное обновление, когда новое состояние зависит от предыдущего?
- Нет ли дублирующего состояния, которое можно вычислять из props или другого state?
- Не возникают ли рассинхронизации между локальным и глобальным состоянием?
- Не хранится ли в state то, что должно находиться в ref?
- Не используется ли ref вместо state для данных, влияющих на отображение?
- Не сбрасывается ли состояние неожиданно при изменении key?
- Не хранится ли один и тот же серверный ресурс одновременно в нескольких независимых хранилищах?
- Не содержит ли компонент слишком много ответственности?
- Корректно ли разделены бизнес-логика, состояние и представление?
- Нет ли чрезмерной вложенности JSX?
- Не дублируется ли одинаковая логика между компонентами?
- Не создаются ли ненужные абстракции ради нескольких строк кода?
- Совпадает ли key со стабильной идентичностью элемента?
- Не используется ли индекс массива как key в динамических списках, где это может нарушить идентичность?
- Не передаются ли через props значения, которые компоненту не нужны?
- Не используется ли Context там, где достаточно локального состояния или props?
- Корректно ли применяются compound components, controlled и uncontrolled patterns?
- Нет ли ошибок при условном отображении (0, null, undefined, пустые массивы)?
- Корректно ли обрабатываются состояния загрузки, ошибки и отсутствия данных?
- Нет ли лишних ререндеров компонентов?
- Установлена ли причина ререндеров, прежде чем предлагать оптимизацию?
- Не подписывается ли компонент на слишком большой фрагмент глобального состояния?
- Используются ли селекторы Zustand/Redux для точечных подписок?
- Не создаются ли новые объекты, массивы и функции там, где их идентичность действительно влияет на производительность?
- Не используются ли useMemo, useCallback, memo без измеримой необходимости?
- Нет ли дорогостоящих вычислений при каждом рендере?
- Не блокируют ли тяжёлые синхронные операции основной поток?
- Виртуализированы ли действительно большие списки, если обычный рендер вызывает проблемы?
- Используются ли debounce/throttle для высокочастотных событий там, где это необходимо?
- Нет ли ненужного обновления всего дерева компонентов при изменении одного поля?
- Не вызывается ли чрезмерное количество запросов из-за ререндеров?
- Нет ли утечек памяти из-за долгоживущих ссылок или подписок?
- Не ухудшает ли оптимизация читаемость без доказанного выигрыша?


## Пример: stale closure
```tsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <span>{count}</span>;
}
```
`count` захвачен из первого рендера. Значение застрянет на `1`. Исправить на `setCount(value => value + 1)` (или пересмотреть зависимости и жизненный цикл).

## Next.js
- Учитывай фактическую версию Next.js (особенно поведение cache и data fetching).
- Проверяй границу Server/Client Component; использование browser API на сервере приведёт к ошибкам.
- Не доверяй `use client` как защите секрета.
- В Route Handlers/Server Actions проверяй права доступа на сервере, а не только видимость кнопки.
- После мутации проверяй механизм инвалидации/обновления данных (для используемой архитектуры).
- Проверяй обработку `loading`, `error`, `not-found` и ошибочного ответа API.

## Пример: авторизация только в UI
```tsx
{user.isAdmin && <button onClick={deleteUser}>Удалить</button>}
```
Это не делает серверный `DELETE` защищённым: любой клиент может отправить HTTP-запрос. Найди серверную проверку прав; если она отсутствует, это высокий приоритет.

## Не спеши заводить замечание
Не считай каждый `useEffect` ошибкой, каждый отсутствующий `memo` проблемой производительности, а каждый Client Component нарушением. Нужны конкретные последствия.
