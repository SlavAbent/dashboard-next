# Prisma и PostgreSQL

## Общие правила

- Используй существующую Prisma Schema, Prisma Client и принятые в проекте паттерны доступа к БД.
- Не вызывай Prisma напрямую из контроллера, если доступ к данным выделен в репозитории.
- Выбирай только нужные поля, если это уменьшает избыточный доступ.
- Фильтруй в БД, когда это корректнее и эффективнее.
- Учитывай пагинацию, связи, N+1, индексы и уникальные ограничения.

### Проекция

```ts
const users = await prisma.user.findMany({
  select: { id: true, name: true },
});
```

### Фильтрация

Плохо при большом наборе:

```ts
const users = await prisma.user.findMany();
const active = users.filter(user => user.isActive);
```

Лучше:

```ts
const active = await prisma.user.findMany({
  where: { isActive: true },
});
```

Примеры предполагают существование указанных полей в текущей схеме.

## Транзакции

Используй атомарные операции, когда несколько изменений должны фиксироваться вместе.

```ts
await prisma.$transaction(async tx => {
  await tx.account.update({
    where: { id: accountId },
    data: { balance: { decrement: amount } },
  });
  await tx.transaction.create({
    data: { accountId, amount, type: 'withdrawal' },
  });
});
```

Это **не готовый код списания денег**: нужны проверка достаточности средств, защита от конкурентных изменений, идемпотентность и соответствующие ограничения БД.

## Миграции

- Сначала оцени, требуется ли изменение схемы.
- Не выполняй разрушительные миграции и очистку данных без явного согласования.
- Учитывай существующие строки и совместимость приложения во время развёртывания.
- Проверяй последствия новых индексов, ограничений, nullable-полей и каскадного удаления.
- Не утверждай, что миграция применена, если она лишь создана.
