# Планирование архитектурных изменений

## Стратегия небольших шагов
1. Зафиксируй текущее наблюдаемое поведение тестами.
2. Наметь новую границу и договорись о её контракте.
3. Перемещай одну ответственность за раз.
4. Сохраняй совместимые экспорты/адаптеры на переходный период.
5. Запускай проверки после каждого логического изменения.
6. Удали старый слой только когда все вызовы переведены.

## Пример: отделить бизнес-логику от контроллера
Было:
```ts
async function create(req, res) {
  if (!req.body.title?.trim()) return res.status(400).json({ error: 'title' });
  const task = await prisma.task.create({ data: { title: req.body.title } });
  res.status(201).json(task);
}
```
Стало:
```text
route -> controller (HTTP) -> service (инвариант) -> data access (Prisma)
```
При миграции сохрани статус, структуру успешного ответа и формат ошибок, если изменение API не было частью задачи.

## Риски
- Циклические зависимости после разделения модулей.
- Разрушенные импорты и public API.
- Непреднамеренные изменения транзакционных границ.
- Риск расхождения схемы БД и DTO.
- Регрессии авторизации.

## Критерии завершения
- Старое поведение сохранено либо документировано изменение.
- Тесты и проверки типов проходят (если запускались).
- Новые границы имеют ясную ответственность.
- Нет дублирующих реализаций, оставленных без причины.
- Известны план отката и ограничения.

Не выполняй массовое переименование модулей в одной операции без необходимости. Если цель — только схема архитектуры, не модифицируй проект.
