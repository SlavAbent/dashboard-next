# React Testing Library — тесты интерфейса

## Приоритет запросов
Используй `getByRole`, `getByLabelText`, `findByRole`; `data-testid` — запасной вариант, если нет подходящего доступного селектора.

## Пример интерактивного компонента
```tsx
function Counter() {
  const [count, setCount] = React.useState(0);
  return <button onClick={() => setCount(v => v + 1)}>Счётчик: {count}</button>;
}

test('увеличивает значение после клика', async () => {
  const user = userEvent.setup();
  render(<Counter />);
  await user.click(screen.getByRole('button', { name: 'Счётчик: 0' }));
  expect(screen.getByRole('button', { name: 'Счётчик: 1' })).toBeInTheDocument();
});
```
Предполагается, что `render`, `screen`, `userEvent` и расширения матчеров подключены в проекте.

## Асинхронность
- Для элемента, который появляется позже, применяй `findByRole`.
- Для ожидания изменения условия применяй `waitFor`, но не помещай внутрь побочные действия, вызывающие повторную мутацию.
- Проверяй `loading` → `success`/`error` и корректность доступного текста.

## Формы
- Отправка валидных данных.
- Обязательные поля и ошибки валидации.
- Недоступность submit при отправке, если это требование.
- Показ серверной ошибки и восстановление UI.

## Антипример
```tsx
expect(container.querySelector('.button-primary')).not.toBeNull();
```
Класс не доказывает пользовательское поведение. Предпочитай доступную роль и имя.

## Принципы
Не тестируй напрямую `useState` и внутренние методы компонента. Не высмеивай доступность: если элемент нельзя надёжно найти по роли/названию, это повод оценить семантику разметки.
