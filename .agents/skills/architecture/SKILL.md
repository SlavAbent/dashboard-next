# Architecture — проектирование с учётом компромиссов

**Цель:** выбрать минимально достаточную архитектуру, которая удовлетворяет текущим требованиям, масштабированию, безопасности и поддерживаемости. Архитектура — не набор обязательных паттернов.

## Алгоритм
1. Прочитай `AGENTS.md`, изучи текущую структуру, объём изменений и реальные ограничения.
2. Сформулируй функциональные и нефункциональные требования; разделяй известные факты и допущения.
3. Прочитай **[references/decision-process.md](references/decision-process.md)** и только подходящие тематические файлы.
4. Предложи 2–3 разумных варианта, если выбор неочевиден. Сравни по сложности, границам ответственности, рискам миграции, тестируемости и операционным затратам.
5. Выбери минимально достаточный вариант и объясни, почему альтернативы не подходят сейчас.
6. Если пользователь просит только дизайн, не переписывай код. Если просит реализовать, меняй систему поэтапно с контролем совместимости.

## Цикл архитектурного этапа

1. Проанализируй фактическое состояние и подготовь проверяемый план без изменения кода.
2. Проверь план против требований, существующих контрактов, потребителей, рисков и доступных проверок.
3. Если существенный выбор нельзя сделать без пользователя, верни `ARCHITECTURE_NEEDS_DECISION`, варианты и конкретный вопрос.
4. Если план неполон, уточни его внутри текущего этапа и повтори самопроверку.
5. Когда план готов, верни `ARCHITECTURE_READY`, нумерованный checklist, критерии приёмки, риски и команды проверки.
6. После замечаний пользователя обнови план и снова пройди самопроверку. Не переходи к реализации самостоятельно.

Архитектурный этап считается завершённым только после явного одобрения плана пользователем. До одобрения не изменяй код, конфигурацию, зависимости и данные.

## Формат ответа
1. **Контекст и требования** (включая допущения).
2. **Предлагаемая схема** (модули, направления зависимостей, ответственность).
3. **Контракты и поток данных** (ключевые DTO/операции).
4. **Альтернативы и компромиссы**.
5. **Риски и проверка**.
6. **План внедрения** — только если требуется реализация/миграция.

Не внедряй Clean Architecture, микросервисы, CQRS, Event Sourcing или репозиторий для каждой сущности без конкретной причины. Не выдавай примерную структуру каталогов за единственно верную.
