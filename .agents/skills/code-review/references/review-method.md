# Методика ревью и система приоритетов

## Что считать проблемой
Дефект должен иметь проверяемую связь **код → условия → наблюдаемый эффект**. Стилевое несоответствие без последствий — не баг. Не требуй абстракций «на будущее». Сначала анализируй изменённые строки, потом вызывающий код и внешние контракты.

## Шаги
1. Установи назначение задачи и ограничь область diff.
2. Проверь контракты: типы, схема БД, HTTP, состояние клиента, кэш, маршруты.
3. Проследи happy path, пустые значения, ошибки сети, конкурентные вызовы и права пользователя.
4. Посмотри тесты; отсутствие теста — замечание только при значимом риске регрессии.
5. Проверь реальные версии инструментов и особенности рантайма, не переноси автоматически знания о другой версии.
6. Для каждого кандидата попробуй опровергнуть собственную гипотезу: есть ли guard, middleware, транзакция, ограничение БД или тест в другом месте?
7. Оставляй только проблемы с достаточной уверенностью; предположения выноси отдельно.

## Приоритеты
- **P1 / Critical:** доступ к чужим данным, обход авторизации, потеря данных, компрометация секретов.
- **P2 / High:** основной сценарий не работает, массовая регрессия, неверная запись в БД.
- **P3 / Medium:** заметный крайний случай, воспроизводимая проблема производительности, частичная ошибка обработки состояния.
- **P4 / Low:** небольшой подтверждённый дефект без серьёзного влияния.

Приоритет зависит от вероятности и масштаба, а не от личной оценки стиля.

## Пример корректного замечания
```ts
const result = users.find((user) => user.id === id);
return result.name;
```

> **[P3] Обработать отсутствующего пользователя — `src/users.ts:18–19`**. Если `id` отсутствует в массиве, `find` вернёт `undefined`, а обращение к `.name` вызовет `TypeError`. Добавить обработку отсутствующего пользователя с явным контрактом возврата или ошибкой.

Неверно: «лучше переписать на reduce» — не связано с дефектом.

## Шаблон финала
1. Findings — упорядоченные по важности.
2. Questions / assumptions — только если существенны.
3. Verified — фактические команды и результаты.
4. Summary — охват и известные ограничения.

Если изменения корректны: «Подтверждённых проблем в просмотренном diff не обнаружено. Проверены: …; не проверены: …». Не заявляй, что дефектов точно нет.
