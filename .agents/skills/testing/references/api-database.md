# Тестирование API, Express, Prisma и PostgreSQL

## Уровни
- **Service unit:** мок репозитория, проверка бизнес-инвариантов.
- **HTTP integration:** запрос к приложению, проверка статуса, заголовков, JSON и ошибок; моки или тестовая БД по архитектуре.
- **DB integration:** настоящая отдельная тестовая БД, проверка схемы, ограничений и транзакций.

## Пример service unit
```ts
const repo = { findById: jest.fn().mockResolvedValue(null) };
const service = createTaskService(repo);
await expect(service.getById('missing')).rejects.toMatchObject({ code: 'NOT_FOUND' });
expect(repo.findById).toHaveBeenCalledWith('missing');
```
Пример предполагает фабрику сервиса и доменный тип ошибки `NOT_FOUND`; адаптируй к реальному проекту, не создавай их ради копирования фрагмента.

## HTTP-контракт
Для `POST /tasks` обычно проверяй:
1. Успех: ожидаемый код, идентификатор, форма JSON.
2. Невалидное тело: 400/422 согласно принятому контракту.
3. Неавторизованный пользователь: 401.
4. Пользователь без права: 403 (либо скрывающий существование 404 по политике API).
5. Конфликт: 409, если контракт предусматривает.

## Тестовая БД
- Используй отдельную DATABASE_URL, никогда production.
- Данные очищай между тестами безопасно.
- Учитывай параллельные тесты и уникальные идентификаторы.
- Миграции прогоняй на тестовом окружении; не применяй `db push --force-reset` на реальной БД.
- Для транзакций проверь, что при ошибке не остаётся частичных записей.

## Пример инварианта
После ошибки при создании связанной записи `payment` баланс аккаунта не должен быть списан. Проверяй итоговое состояние БД, а не только факт вызова `$transaction`.

## Безопасность
Не печатай токены, пароли, cookie и реальные персональные данные в отчёте тестов.
