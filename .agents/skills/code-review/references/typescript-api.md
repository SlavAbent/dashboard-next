# Code Review: TypeScript и API-контракты

## TypeScript
- Опасные `any`, `as`, `!`, `@ts-ignore` в местах, где нарушается реальная гарантия.
- Исчерпывающая обработка discriminated unions при смене статуса.
- Различие между `undefined`, `null`, пустой строкой и отсутствием поля.
- Неверное сочетание optional fields с частичным обновлением.
- Несовместимость DTO, доменной модели и ответа сервера.

## Пример: тип утверждён, но не проверен
```ts
const user = (await response.json()) as User;
return user.id.toUpperCase();
```
`as User` не проверяет ответ сервера. Если API вернёт `{ id: null }`, операция упадёт. Нужна runtime-валидация на границе недоверенных данных, когда формат не гарантирован.

## HTTP
- `fetch` не отклоняет Promise из-за статусов 400–599: должна быть проверка `response.ok`.
- Различай 401 (нет аутентификации) и 403 (нет права).
- Проверяй код/тело ответа для 204: `response.json()` на пустом теле может выбросить ошибку.
- Учитывай отмену запросов, race condition, идемпотентность мутаций.
- Не передавай стек ошибок, токены и приватные данные во внешние ответы.

## Пример: некорректная обработка 404
```ts
const response = await fetch('/api/users/42');
const user = await response.json();
return user.name;
```
HTTP 404 не вызовет исключение сам по себе. Без `response.ok` код может интерпретировать тело ошибки как пользователя.

## Как оформлять замечание
Укажи **конкретный ответ/вход**, при котором типовое обещание нарушается, и где это приводит к падению или порче данных. Не ругай просто `interface` против `type`: это конвенция, а не дефект.
