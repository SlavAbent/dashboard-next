# API, BFF и интеграция сервисов

## Контракт API
Определи:
- Маршруты/методы и их назначение.
- Входные данные (path/query/body) и runtime-валидацию.
- DTO ответов, статусы 200/201/204/400/401/403/404/409/500 по смыслу.
- Пагинацию, сортировку, фильтрацию при необходимости.
- Поведение при повторном запросе и ошибках.
- Версионирование или стратегию изменения контракта.

## Пример
```http
POST /api/tasks
Content-Type: application/json

{"title":"Прочитать документацию"}
```
```json
{"id":"task_123","title":"Прочитать документацию","status":"planning"}
```
`ownerId` устанавливается на сервере из доверенной сессии, а не берётся без проверки из клиентского body.

## Когда BFF оправдан
- Сборка данных из нескольких backend-источников.
- Адаптация ответов под конкретный frontend.
- Серверная работа с секретами и сессией.
- Стабильный контракт UI при изменениях upstream API.

Не создавай BFF-прокси без необходимости, если frontend может безопасно обращаться к существующему API.

## Realtime/WebSocket
- Определи модель авторизации соединения.
- Схему событий и их версии.
- Политику повторного подключения и дедупликации.
- Источник истины, порядок сохранения и рассылки сообщений.

## Пример последовательности
```text
Client -> BFF -> Service -> Repository -> PostgreSQL
                  |                         |
                  +------- результат -------+
BFF -> Client: DTO ответа
```

В асинхронной системе уточни гарантию доставки (at-most-once, at-least-once), необходимость идемпотентности и восстановление после переподключения.
