# Моделирование данных: Prisma и PostgreSQL

## Дизайн схемы
- Определи сущности и отношения 1:1, 1:N, M:N.
- Для важных инвариантов используй ограничения БД, а не только валидацию UI.
- Укажи unique, foreign keys, nullable, cascade-политику.
- Индексы основывай на реальных фильтрах и объёмах.
- Не выбирай денормализацию «на всякий случай».

## Пример Prisma
```prisma
model Task {
  id        String   @id @default(cuid())
  title     String
  ownerId   String
  createdAt DateTime @default(now())
  owner     User     @relation(fields: [ownerId], references: [id])

  @@index([ownerId, createdAt])
}
```
Предполагается наличие модели `User` с обратным полем связи. Это демонстрация индекса для списка задач пользователя, а не полная schema.

## Транзакционные границы
Если две записи образуют один бизнес-инвариант, проектируй их атомарное изменение. Транзакция устраняет частичную запись, но сама по себе не решает все проблемы конкурентных операций; продумай изоляцию, блокировки или условные обновления.

## Запросы
- Используй `select`/`include` намеренно.
- Оцени N+1, объём ответа и пагинацию.
- Анализируй `EXPLAIN ANALYZE` при реальных проблемах запроса.
- Исключи секретные поля из DTO.

## Миграции
Разделяй изменение схемы и безопасный перенос данных при необходимости. Для потенциально опасных изменений применяй expand → migrate/backfill → contract. Планируй rollback/roll-forward. Не запускай разрушительные миграции на проде без явного согласования.
