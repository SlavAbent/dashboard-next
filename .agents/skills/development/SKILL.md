# Development

Цель: вносить минимальные, корректные, безопасные и поддерживаемые изменения с учётом существующего проекта.

## Перед изменениями

1. Прочитай применимые инструкции проекта (`AGENTS.md`) и изучи связанные файлы.
2. Уточни фактические версии библиотек, конфигурацию и команды из `package.json`.
3. Найди уже существующие решения, интерфейсы, сервисы, компоненты и тесты.
4. Определи минимальный объём изменений и связанные риски.
5. Загрузи **только необходимые** референсы по таблице ниже. Если задача затрагивает несколько слоёв, используй несколько файлов.

## Какие референсы читать

| Когда | Файл |
| --- | --- |
| Всегда: стиль, простота, SOLID/DRY/KISS/YAGNI, изменение существующего кода | [references/principles.md](references/principles.md) |
| Типы, API-контракты, generics, `unknown`, строгий TypeScript | [references/typescript.md](references/typescript.md) |
| Компоненты, hooks, state, эффекты, рендеринг | [references/react.md](references/react.md) |
| App Router, Server/Client Components, Route Handlers, загрузка данных | [references/nextjs.md](references/nextjs.md) |
| Express, REST, controllers/services/repositories, обработка ошибок | [references/backend.md](references/backend.md) |
| Prisma, PostgreSQL, транзакции, запросы, миграции | [references/database.md](references/database.md) |
| Авторизация, валидация, производительность, утечки и безопасность | [references/security-performance.md](references/security-performance.md) |

**Правило выбора:** не читай все файлы автоматически. `principles.md` обязателен для задач с изменением кода, остальные — по затронутым технологиям и рискам. При обработке данных, авторизации и публичного API обязательно читай `security-performance.md`.

## Во время реализации

- Сохраняй текущую архитектуру и публичные контракты, если изменение не требуется задачей.
- Не добавляй зависимости, абстракции и несвязанные изменения без необходимости.
- Учитывай валидацию входных данных, обработку ошибок, асинхронность и безопасность.
- Приоритет: корректность → безопасность → читаемость → поддерживаемость → измеримая производительность.
- Примеры в референсах иллюстрируют принципы, а не являются обязательными шаблонами.

## Цикл разработки

1. Работай только по явно одобренному плану и отмечай выполненные пункты checklist.
2. Реализуй минимальный связный шаг, проверь затронутый diff и запусти релевантную быструю проверку.
3. Если проверка выявила дефект в текущем изменении, исправь его и повтори шаг.
4. При получении findings от code review или дефекта продукта от testing исправляй только подтверждённую проблему, затем повторяй релевантные проверки.
5. После исправления всегда возвращай изменение на code review; не передавай непроверенный diff сразу в testing.
6. Если один и тот же блокер повторился три раза, требуется расширить одобренный scope или получить новое разрешение, верни `DEVELOPMENT_BLOCKED` с доказательствами и не продолжай бесконечные попытки.
7. Когда все одобренные пункты реализованы и первичные проверки завершены, верни `DEVELOPMENT_READY_FOR_REVIEW`.

В handoff укажи выполненные пункты плана, изменённые файлы, точные команды и результаты, а также оставшиеся риски. Не меняй самовольно утверждённые критерии приёмки.

## После реализации

1. Проверь diff и отсутствие случайных изменений.
2. Выполни доступные релевантные команды typecheck, lint, tests из проекта.
3. Не утверждай, что проверка пройдена, если она не запускалась.
4. Кратко отчитайся на русском: что изменено; какие файлы; результаты проверок; известные ограничения.

При конфликте общих рекомендаций с реальными ограничениями проекта придерживайся более специфичных действующих инструкций и явно фиксируй важные компромиссы.
