# Фундаментальные правила тестирования

## Проверяй поведение, а не реализацию
Тест должен отвечать: «Что пользователь или вызывающий код получает на конкретном входе?» Не привязывайся к private state, внутренним именам методов, DOM-структуре без необходимости.

## Arrange → Act → Assert
```ts
test('сумма двух чисел', () => {
  // Arrange
  const a = 2;
  const b = 3;
  // Act
  const result = add(a, b);
  // Assert
  expect(result).toBe(5);
});
```

## Сценарии
- Основной путь (happy path).
- Границы: пустой массив, 0, большое значение, пустая строка.
- Отрицательные случаи: ошибка сети, невалидный ввод, отсутствие записи.
- Права: доступ к своему/чужому ресурсу.
- Асинхронность: отмена, повторный вызов, гонка (если возможна).

## Названия
Хорошо: `it('возвращает 404, если задача не найдена')`.
Плохо: `it('works')`.

## Независимость
Каждый тест готовит собственные данные. Не полагайся на порядок запуска, текущее время или реальную внешнюю сеть. Внешние зависимости изолируй на выбранной границе теста.

## Антипример
```ts
await createTask(input);
expect(true).toBe(true);
```
Действие вызвано, но результат не подтверждён. Проверяй возвращаемое значение, состояние БД, UI или ответ HTTP согласно уровню теста.

## Пропорциональность
Не обязательно покрывать каждую строку. Приоритет: бизнес-инварианты, пользовательские сценарии, ветки ошибок, права доступа и ранее исправленные дефекты. Coverage — индикатор, не самоцель.
