# Code Review — поиск доказуемых проблем

**Цель:** обнаружить ошибки, которые влияют на корректность, безопасность, надёжность или сопровождение. Не превращай ревью в перечень субъективных стилевых предпочтений.

## Процесс
1. Определи объект ревью: diff/PR, файлы или модуль; если не указан, начни с актуального diff. Не считай весь репозиторий изменённым.
2. Изучи `AGENTS.md`, вызывающий код, типы, тесты и конфигурацию. Учитывай версию библиотек и реальный поток данных.
3. Прочитай **[references/review-method.md](references/review-method.md)** и тематические референсы по таблице ниже.
4. Для каждого замечания установи точный сценарий воспроизведения и его последствия. Где возможно, проверь гипотезу статически или тестом без изменения файлов.
5. Не исправляй код, если запрос только на ревью. Не утверждай о выполненных командах, если не запускал их.

| --- | --- |

При ревью fullstack-изменения открывай несколько релевантных файлов; не загружай все автоматически.

## Цикл code review

1. Проверь текущий diff относительно одобренного плана и критериев приёмки.
2. Если есть подтверждённые проблемы, верни `REVIEW_CHANGES_REQUIRED` и findings в порядке приоритета.
3. После исправлений повторно проверь изменившийся diff, затронутые пути выполнения и риск регрессии; не считай прежнее ревью действительным автоматически.
4. Повторяй review после каждого изменения production-кода или тестов, влияющих на доказательство поведения.
5. Если проверку нельзя завершить из-за отсутствующего контекста, разрешения или окружения, верни `REVIEW_BLOCKED` и точно укажи недостающие данные.
6. Когда блокирующих findings нет, верни `REVIEW_APPROVED`, границы ревью и остаточные неблокирующие риски.

Блокирующим считается подтверждённый дефект, нарушающий требования, безопасность, корректность, совместимость или обязательные критерии приёмки. Не задерживай цикл из-за субъективного стиля.

## Формат ответа
Сначала список **подтверждённых проблем**, отсортированный по приоритету. Для каждой:
- **[P1/P2/P3/P4] Краткий заголовок** — `путь:строки`.
- **Доказательство:** что именно в коде приводит к дефекту и при каких условиях.
- **Последствие:** конкретный эффект для пользователя/системы.
- **Исправление:** минимальное действие, без большого несвязанного рефакторинга.

Затем: **Вопросы/непроверенные гипотезы** (отдельно, если есть); **Проверки** (что реально запускалось); **Итог** (включая «подтверждённых проблем не обнаружено», если так).

Указывай реальные диапазоны строк, не выдумывай номера. Не публикуй секреты из кода/логов. Примеры из референсов — образцы рассуждения, а не автоматически применимые замечания.
