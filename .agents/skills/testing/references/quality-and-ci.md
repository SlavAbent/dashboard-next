# Качество тестов, edge cases и CI

## Минимальная матрица сценариев
| Тип | Что проверять |
| --- | --- |
| Успех | Основной наблюдаемый результат |
| Валидация | Пустые, неверные, слишком большие данные |
| Сбой зависимости | API/БД недоступны, таймаут, отмена |
| Авторизация | Свой и чужой ресурс |
| Конкурентность | Повторная отправка, двойной клик, гонка запросов |
| Состояние | Loading → success/error → retry |

## Диагностика упавшего теста
1. Прочитай ошибку и ожидаемое/фактическое поведение.
2. Определи, сбой в тесте, окружении или продукте.
3. Воспроизведи адресно, затем проверь полный затронутый набор.
4. Не добавляй `skip`, увеличенный timeout или retry как первый ответ.
5. Не исправляй ассерт на неправильное значение ради зелёного результата.

## Flaky tests
Частые причины: ожидание по времени, общий mutable state, недетерминированные часы, случайные данные, сеть, нарушение независимости, параллельные записи в БД.

Плохо:
```ts
await new Promise(resolve => setTimeout(resolve, 2000));
expect(result).toBe('ready');
```
Лучше дождаться наблюдаемого условия средствами выбранного инструмента.

## Coverage
Доля строк не доказывает корректность. Значимые asserts и критические ветки важнее процента. Если пользователь требует порог, используй существующие инструменты проекта и честно сообщай цифры.

## CI
- Команды берутся из scripts и конфигурации, а не выдумываются.
- Не требуй секретов/production-доступа для проверки локального изменения.
- Явно разделяй «прошло», «упало», «не запускалось».
