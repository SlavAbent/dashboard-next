# Процесс архитектурного решения и ADR

## Сначала требования
Раздели:
- **Functional:** что должна делать система (создание задачи, авторизация, чат).
- **Non-functional:** нагрузка, задержки, устойчивость, безопасность, стоимость, SLA.
- **Constraints:** стек, команда, сроки, совместимость, инфраструктура.
- **Unknowns:** что неизвестно, какие допущения сделаны.

## Оцени вариант по критериям
- Минимальная стоимость изменения.
- Чёткая ответственность модулей.
- Управление зависимостями.
- Проверяемость и изолированность тестами.
- Наблюдаемость, отказоустойчивость, безопасность.
- Цена поддержки и перехода с текущей реализации.

## Пример выбора
Задача: небольшое API задач с PostgreSQL. Варианты:
1. **Route → Service → Prisma:** достаточно для небольшого модуля при хорошей изоляции HTTP.
2. **Route → Controller → Service → Repository:** полезно при сложных сценариях, нескольких хранилищах или повторном использовании бизнес-операций.
3. **Clean Architecture с ports/adapters:** возможна при строгих требованиях к независимости домена, но несёт больше интерфейсов и конфигурации.

Не создавай дополнительные слои автоматически. Выбор обоснуй реальными требованиями.

## Шаблон ADR
```md
# ADR-001: Выбор организации доступа к данным

Статус: принято
Контекст: ...
Решение: ...
Альтернативы: ...
Последствия (+/-): ...
Критерии пересмотра: ...
```

## Проверка решения
«Как изменится архитектура, если добавим новую сущность, новый источник данных, другой механизм авторизации?» Непропорциональное число изменяемых модулей — сигнал чрезмерной связанности, но не всегда аргумент за новую абстракцию.
